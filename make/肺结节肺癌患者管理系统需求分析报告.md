# 肺结节/肺癌患者管理系统——需求分析调研报告

> 技术背景：Spring Boot + Spring Cloud 微服务架构
> 报告用途：毕业设计/课程设计的需求分析阶段参考

---

## 一、项目背景与立项意义

### 1.1 疾病背景

- **肺癌是我国发病率和死亡率均居首位的恶性肿瘤**。随着低剂量螺旋 CT（LDCT）筛查和高分辨率 CT（HRCT）的普及，肺结节检出率显著上升，体检人群中肺结节检出已非常普遍，其中绝大多数为良性，但需要长期、规范的随访观察 [^11^][^9^]。
- **随访依从性差是行业核心痛点**。肺结节和肺癌术后患者需要在 3 个月、6 个月、1 年、2 年甚至更长时间跨度上反复复查。大量患者因遗忘、焦虑、对结节认知不足等原因"失联"，导致随访漏网、流失，延误恶性结节的干预时机。胸科临床专家明确指出，专科结节门诊和**严密追踪系统**的建立能极大减少随访"漏网""流失"现象，提升全程管理的安全性和规范性 [^10^]。
- **随访规则复杂且高度依赖指南**。结节类型（实性/部分实性/磨玻璃）、大小阈值、患者危险因素、术后病理分期、基因突变状态等都会影响随访频率，人工管理容易出错，亟需信息化系统内置指南规则进行自动化管理。

### 1.2 政策与行业趋势

- 国家推动"互联网+医疗健康"和分级诊疗，医院采购的肿瘤慢病管理系统已明确包含"自动化个性化随访、患者报告结局（ePRO）管理、患者端移动工具、数据驾驶舱"等要求 [^31^]。
- 国内多项专家共识（《肺结节诊治中国专家共识（2024 年版）》《多发磨玻璃结节样肺癌多学科诊疗中国专家共识（2024 年版）》《肺结节精准管理专家共识（2026 版）》）推动肺结节管理走向规范化、个体化、多学科（MDT）协作 [^5^][^8^][^9^]。
- 研究证实，基于微信小程序的肺癌术后个性化随访（集成症状量表与预警阈值）能显著提升患者生活质量和自我管理效能 [^1^]，说明"系统 + 移动端随访"模式已有循证支持。

### 1.3 项目意义

构建一个覆盖"筛查建档 → 风险评估 → 随访计划自动生成 → 智能提醒 → 复查结果录入 → 结节动态对比 → 转诊/治疗跟踪"全流程的管理系统，将指南规则引擎化，解决患者失访、医生人工排期繁重、随访数据分散三大问题。

## 二、临床业务流程调研

### 2.1 肺结节患者管理流程（核心业务流程）

```
体检/门诊发现结节（CT 报告）
      ↓
建档录入：患者基本信息 + 危险因素评估（年龄、吸烟史、家族史、职业暴露等）
      ↓
结节登记：类型（实性/部分实性/纯磨玻璃）、大小、位置、数量、恶性征象
（分叶、毛刺、胸膜牵拉、空泡征、血管集束等）
      ↓
风险分层：低危 / 中危 / 高危（参照 Lung-RADS 或中国专家共识 C-Lung-RADS 分级）
      ↓
系统按规则引擎自动生成随访计划（见 3.2 随访规则库）
      ↓
到点自动提醒（短信/站内信/微信推送）→ 患者复查 → 录入复查结果
      ↓
结节前后对比（大小、密度、实性成分变化）
      ├─ 稳定/缩小 → 按原计划继续随访（可降级）
      ├─ 增大/实性成分增加 ≥2mm → 升级随访间隔或转入 MDT 会诊 [^12^]
      └─ 高度疑恶性 → 转胸外科/介入路径（活检、PET-CT、手术）
```

### 2.2 肺癌术后患者管理流程

```
手术/治疗完成 → 录入病理分期（TNM）、基因检测结果（EGFR/ALK 等）、
                治疗方案（是否辅助治疗）
      ↓
系统按分期+驱动基因状态匹配术后随访方案（见 3.3）
      ↓
周期性随访：病史/查体、肿瘤标志物（CEA、CYFRA21-1、NSE、SCC、CA125）、
胸部 CT、腹部影像、头颅 MRI、骨扫描等 [^21^]
      ↓
症状主动上报（ePRO）：疼痛、咳嗽、乏力等异常实时预警医护 [^1^][^31^]
      ↓
复发/转移 → 转入再治疗管理；稳定 → 按计划继续随访至 5 年以上
```

### 2.3 多学科会诊（MDT）流程

高危结节（如实性结节 ≥15mm 或 8~15mm 伴恶性征象）应由胸外科、肿瘤内科、呼吸科、影像科医师集体会诊决定诊疗方案 [^3^]。系统可设计 MDT 会诊申请、会诊记录、结论归档模块作为扩展功能。

## 三、随访规则知识库（系统规则引擎的核心依据）

### 3.1 结节风险分层（Lung-RADS 简表）

| 分类 | 含义 | 随访建议 |
|---|---|---|
| 1 类 | 阴性/无结节 | 每年 1 次 LDCT |
| 2 类 | 良性表现 | 每年 1 次 LDCT |
| 3 类 | 可能良性 | 6 个月 LDCT 复查 |
| 4A 类 | 可疑恶性 | 3 个月 LDCT 复查；实性成分 ≥8mm 可 PET/CT |
| 4B/4X 类 | 高度可疑 | 增强 CT、PET-CT、活检/进一步评估 |

来源：美国放射学会 Lung-RADS 分级随访建议 [^15^][^20^]。2024 版中国共识引入 C-Lung-RADS，将结节分为低危、中危、高危、极高危四级 [^12^]。

### 3.2 肺结节随访规则（依据《肺结节诊治中国专家共识（2024 年版）》）

**孤立性实性结节 ≤8mm 且无危险因素** [^7^]：

| 结节大小 | 随访策略 |
|---|---|
| ≤4mm | 由有经验医生建议随访；不随访需告知风险 |
| 4~6mm | 常规年度随访 |
| 6~8mm | 2 年内 6~12 个月随访一次，无变化转年度随访 |

**孤立性实性结节 ≤8mm 且有危险因素（吸烟、家族史等）** [^7^]：

| 结节大小 | 随访策略 |
|---|---|
| ≤4mm | 常规年度随访 |
| 4~6mm | 6~12 个月随访，无变化 18~24 个月再随访，后转年度 |
| 6~8mm | 首次 3~6 个月随访，随后 9~12 个月，之后每 6 个月，2 年无变化转年度 |

**磨玻璃/部分实性结节** [^5^][^13^]：

| 结节类型 | 大小 | 随访策略 |
|---|---|---|
| 纯磨玻璃（pGGN） | ≤5mm | 首次 6 个月 CT 随访，随后年度随访 |
| 纯磨玻璃（pGGN） | >5mm | 3 个月 CT 确认，无变化后年度随访；>10mm 考虑活检/手术 |
| 部分实性（mGGN） | ≤8mm | 3、6、12、24 个月 CT 随访，无变化转年度，总随访 ≥3 年 |
| 部分实性（mGGN） | >8mm | 3 个月复查；持续存在则 PET、活检和/或手术评估 |

**结节增大处理**：随访中结节增大或实性成分增加 ≥2mm，建议升级随访策略（缩短间隔）或转入进一步检查 [^12^]。

### 3.3 肺癌术后随访规则（依据卫健委指南/胸外科专家共识/CSCO）

| 患者类别 | 随访频率 | 主要项目 |
|---|---|---|
| 原位癌 | 每年 1 次 | 低剂量螺旋 CT + 常规体检 [^21^][^27^] |
| I 期（无需辅助治疗，驱动基因阴性） | 前 2 年每 6 个月 1 次，第 3 年后每年 1 次 | 方案 A（局部：病史、查体、肿瘤标志物、胸部 CT）与方案 B（全身：腹部 CT/B 超、头颅增强 MRI、骨扫描或 PET-CT）交替 [^21^] |
| II~III 期（需辅助治疗） | 前 2 年每 3 个月 1 次，第 3~5 年每 6 个月 1 次，5 年后每年 1 次 | 方案 A/B 交替 [^21^][^27^] |
| EGFR 阳性需辅助治疗 | 前 3 年每 3 个月 1 次，第 4~6 年每 6 个月 1 次，6 年后每年 1 次 | 同上 [^27^] |
| IV 期全身治疗结束后 | 每 6~8 周 1 次 | CSCO 指南 [^26^] |
| 局限期小细胞肺癌术后 | 前 2 年每 3 个月，第 3 年每半年，第 4 年后每年 | 胸腹盆增强 CT、头颅 MRI、骨扫描、肿瘤标志物、戒烟评估 [^21^] |

> **系统设计启示**：随访频率不是固定值，而是由"结节类型 + 大小 + 危险因素"或"分期 + 基因状态 + 是否辅助治疗"组合决定的。建议将上表固化为可配置的**规则模板（随访方案模板库）**，医生可为患者选择模板后个体化微调。

## 四、用户角色与痛点分析

### 4.1 角色定义

| 角色 | 职责 | 核心诉求 |
|---|---|---|
| **系统管理员** | 用户/角色/权限管理、规则模板维护、数据字典、日志审计 | 配置灵活、操作留痕 |
| **医生（呼吸科/胸外科/肿瘤科）** | 审核建档、风险分层、制定/调整随访方案、查看复查对比、处理预警 | 减少人工排期、异常患者优先呈现 |
| **随访专员/护士** | 执行电话/线上随访、录入随访结果、追踪失访患者 | 待办列表清晰、可批量操作、随访话术模板 |
| **患者** | 接收复查提醒、查看随访计划与健康宣教、上报症状、在线咨询 | 不遗漏复查、看得懂的报告解读 |
| **MDT 专家组**（可选） | 高危结节会诊 | 结构化病例资料汇总 |

### 4.2 核心痛点（来自文献与行业调研）

1. **随访流失**：随访时间跨度长（3~5 年甚至终身），患者遗忘或失访率高，需自动提醒与失访追踪机制 [^10^][^22^]。
2. **排期靠人工**：不同结节/分期对应不同复查周期，人工计算易出错，需规则引擎自动生成。
3. **数据分散**：影像、检验、随访记录分散在不同系统，结节前后对比困难，需结构化沉淀结节随访数据。
4. **异常发现滞后**：患者院外症状无人监测，需 ePRO 症状上报 + 阈值预警 [^1^][^31^]。
5. **患者认知不足**：对"磨玻璃结节"过度焦虑或完全忽视，需分层健康宣教与依从性管理 [^20^]。
6. **数字鸿沟**：老年患者占比较高，移动端操作需简单，必要时保留电话随访通道（研究显示约 15% 老年患者需要电话支持）[^1^]。

## 五、功能性需求

### 5.1 功能模块总览

```
肺结节/肺癌患者管理系统
├── 1. 用户与权限管理
├── 2. 患者档案管理
├── 3. 结节/病灶管理
├── 4. 检查检验记录管理
├── 5. 随访计划引擎（核心）
├── 6. 随访执行与预警
├── 7. 消息提醒中心
├── 8. 患者移动端（患者门户）
├── 9. 健康宣教与问卷
├── 10. 统计分析与数据驾驶舱
├── 11. MDT 会诊管理（扩展）
└── 12. 系统管理（字典/模板/日志）
```

### 5.2 各模块需求明细

**1. 用户与权限管理**
- 多角色登录（管理员/医生/随访专员/患者），RBAC 权限模型
- 医生-患者绑定（主管医生负责制）
- JWT 无状态认证 + 网关统一鉴权

**2. 患者档案管理**
- 基本信息： demographics、联系方式、紧急联系人
- 危险因素档案：吸烟史（包年）、家族史、职业暴露、既往肿瘤史、合并症（如 COPD）——危险因素直接影响随访策略选择 [^7^]
- 诊断信息：结节发现方式（体检/门诊/住院）、肺癌分期（TNM）、病理类型、基因检测（EGFR/ALK/ROS1 等）、手术/治疗记录
- 档案标签：结节随访中 / 术后随访中 / MDT 中 / 治疗中 / 失访 / 结案

**3. 结节/病灶管理**
- 结节登记：编号、位置（肺叶/段）、类型（实性/部分实性/纯磨玻璃）、最大径、实性成分径、密度、数量（单发/多发）、恶性征象（分叶/毛刺/胸膜牵拉/空泡/血管集束）
- 每次复查形成一条结节快照，支持同一结节**纵向对比**（大小、体积、密度变化趋势图；体积倍增时间 VDT 是重要指标 [^18^]）
- 新发结节单独标记（新发结节恶性概率相对更高，随访频率更高 [^3^]）

**4. 检查检验记录管理**
- CT/HRCT 报告结构化录入（报告日期、设备、层厚、影像描述、影像结论、影像附件上传）
- 检验记录：肿瘤标志物（CEA、CYFRA21-1、NSE、SCC、CA125）、血常规、生化 [^21^]
- 病理报告、基因检测报告归档（附件上传）

**5. 随访计划引擎（系统核心亮点）**
- 内置规则模板库：结节随访模板（按第三章规则表）、术后随访模板（按分期/基因状态）
- 建档时根据患者特征**自动匹配模板**，生成未来若干年的随访任务时间轴
- 医生可个体化微调（调整间隔、增减项目、提前/延后）
- 复查结果录入后**自动计算下次随访时间**；结节增大/实性成分增加时自动提示升级随访策略 [^12^]
- 随访项目模板：局部方案（病史+查体+标志物+胸部 CT）、全身方案（+腹部影像+头颅 MRI+骨扫描）[^21^]

**6. 随访执行与预警**
- 随访工作台：按"下次随访日期"排序的待办列表，状态分未到期/临期/逾期/已完成/失访 [^22^]
- 随访记录：电话随访、门诊随访、线上随访问卷，支持复制上次记录修改 [^25^]
- 失访管理：逾期 N 天未完成自动标红，多次提醒无效转入失访名单并支持追踪
- 预警规则：症状上报超阈值（如疼痛评分）、标志物异常升高、结节增大 → 实时推送主管医生 [^1^]

**7. 消息提醒中心**
- 复查提醒：到期前 7 天/3 天/1 天多级提醒
- 渠道：站内信 + 短信（可接阿里云/腾讯云短信）+ 微信公众号/小程序模板消息（扩展）
- 消息模板管理、发送记录与送达状态

**8. 患者端（Web 或预留小程序接口）**
- 查看个人随访计划时间轴、下次复查时间与注意事项
- 检查报告查询与趋势图（结节大小变化折线图——很好的可视化亮点）
- 症状上报（ePRO）：疼痛、咳嗽、乏力等分级量表 [^1^][^31^]
- 随访问卷在线填写、在线咨询/留言
- 健康宣教文章推送（戒烟指导、呼吸功能锻炼、结节科普 [^30^][^20^]）

**9. 健康宣教与问卷**
- 宣教内容管理：分类（筛查/随访/术后康复/用药/营养运动）、定向推送（按患者标签）
- 问卷管理：随访问卷模板、症状量表（可参考 MDASI 及肺癌特异性症状模块 [^1^]）、结果自动评分

**10. 统计分析与数据驾驶舱**
- 患者分布（结节类型/风险等级/分期分布）、随访完成率、失访率、结节进展率
- 医生工作量、随访及时率
- 可视化报表（ECharts），支持管理层决策 [^31^]

**11. MDT 会诊管理（扩展）**
- 高危结节一键发起会诊申请（自动汇总结节影像史、危险因素、检验结果）
- 会诊意见记录、结论回写随访方案 [^3^][^8^]

**12. 系统管理**
- 数据字典（结节类型、分期、征象、随访项目）、随访模板配置、操作日志与审计

## 六、非功能性需求

| 类别 | 需求 |
|---|---|
| **安全性** | 医疗数据敏感：密码加密存储（BCrypt）、传输 HTTPS、接口鉴权、数据脱敏展示（身份证/手机号）；操作留痕可追溯 |
| **合规性** | 遵循《个人信息保护法》《数据安全法》及医疗行业数据规范；患者隐私数据最小化收集 |
| **可用性** | 微服务架构下单服务故障不扩散（熔断降级 Resilience4j/Sentinel）；随访提醒等核心链路需可靠投递（消息队列重试） |
| **性能** | 单院日随访量数百至数千级；列表分页查询响应 <1s；定时任务扫描与消息推送走异步 |
| **可扩展性** | 规则模板可配置化，新增指南共识（如 C-Lung-RADS 更新）不改代码；预留与 HIS/PACS/第三方 AI 影像系统对接接口 [^18^] |
| **易用性** | 患者端适配中老年用户：大字体、少步骤；医生端待办驱动式工作台 |
| **可维护性** | 统一配置中心、统一返回体、Swagger/Knife4j 接口文档、链路追踪（SkyWalking/Sleuth） |

## 七、微服务架构设计建议（Spring Boot + Spring Cloud）

参考成熟的医疗/患者管理微服务实践 [^24^][^32^]，建议拆分如下：

| 服务 | 职责 | 关键技术 |
|---|---|---|
| gateway | 统一入口、路由、鉴权、限流 | Spring Cloud Gateway |
| registry / config | 注册中心、配置中心 | Nacos（注册+配置一体，国内主流） |
| auth-service | 登录认证、Token 签发、RBAC | Spring Security + JWT + Redis |
| patient-service | 患者档案、危险因素、诊断信息 | Spring Boot + MyBatis-Plus + MySQL |
| nodule-service | 结节/病灶登记、复查快照、纵向对比 | MySQL + MinIO（影像附件对象存储） |
| exam-service | 检查检验记录、病理/基因报告归档 | MySQL + MinIO |
| followup-service | 随访规则模板、计划生成、随访执行、失访管理 | XXL-Job 定时扫描 + 规则匹配逻辑 |
| notification-service | 短信/站内信/模板消息推送 | RocketMQ/RabbitMQ 异步 + 阿里云短信 SDK |
| patient-portal-api | 患者端专用 BFF 接口（计划查询、症状上报、问卷） | 复用各服务 Feign 调用 |
| statistics-service | 统计分析、数据驾驶舱 | MySQL 聚合 / 可扩展 Elasticsearch |
| common | 统一返回体、异常、常量、Feign DTO | 公共依赖模块 |

**配套中间件**：MySQL（业务库）、Redis（缓存+Token+分布式锁）、RocketMQ/RabbitMQ（提醒消息异步化、随访事件驱动）、MinIO/OSS（报告附件）、XXL-Job（随访任务每日扫描调度）、Knife4j（接口文档）。

**架构亮点（可作为答辩要点）**：
1. **随访规则引擎配置化**：指南随访表固化为模板数据而非硬编码；
2. **事件驱动**：复查结果录入 → 发 MQ 事件 → 自动计算下次随访 + 结节对比分析；
3. **结节纵向对比可视化**：趋势图 + 增大自动预警；
4. **熔断降级 + 网关鉴权 + 链路追踪**体现微服务治理能力。

## 八、同类系统调研小结

- **医院肿瘤慢病管理系统（招标规格）**：要求自动化个性化随访（多场景模板：术后/化疗/康复）、ePRO 症状上报分级预警、患者小程序（咨询/复诊提醒/报告查询/康复推送）、多维度数据驾驶舱、跨机构双向转诊 [^31^]——可直接对标为系统的功能基线。
- **互联网+慢病管理子系统（公共卫生）**：肺疾病随访、恶性肿瘤随访、历史随访复制、复诊集约视图、绩效统计 [^25^]。
- **国外随访平台研究**：Web 端四大模块——患者登记、预警、随访（按下次随访日排序列表）、患者列表；干预手段含电话随访、短信提醒、App 推送、宣教推送 [^22^]。
- **AI 影像方向（扩展空间）**：国际趋势是 AI 检出 + 体积测量 + 结构化报告 + 纵向追踪闭环平台（如 qTrack/qCT），支持 Lung-RADS 集成与体积倍增时间计算 [^18^]——本项目可预留 AI 对接接口作为创新点。
- **微信小程序肺癌随访 RCT 研究**：集成 MDASI 量表 + 阈值预警 + 个体化宣教，显著提升患者生活质量与自我效能；注意依从性随时间下降（第 1 月 92% → 第 4 月 76%），需设计提醒与激励机制 [^1^]。

## 九、可行性分析

- **技术可行性**：Spring Boot/Spring Cloud 生态成熟，Nacos/Gateway/Sentinel 资料丰富；随访规则本质是"条件→周期"映射，无高难度算法，适合学生团队实现。
- **业务可行性**：随访规则有权威指南背书（第三章表格），业务逻辑明确，无需医生深度参与即可完成规则内置；数据可构造模拟患者演示全流程。
- **时间与范围控制**：建议 MVP 优先级——①档案 + ②结节登记 + ③随访计划引擎 + ④提醒 + ⑤复查录入与对比 + ⑥统计；患者端、MDT、ePRO 作为二期扩展。

## 十一、AI 能力集成方案（重点补充章节）

> 背景：指导老师要求系统体现 AI 能力。本章给出 5 个 AI 集成点，按"可行性 × 演示效果"排序，学生团队可按精力选择落地范围。

### 11.1 AI 集成点总览

| 编号 | AI 功能 | 技术路线 | 难度 | 演示效果 | 建议优先级 |
|---|---|---|---|---|---|
| A1 | **CT 报告智能解读**（患者端/医生端） | 大模型 API（DeepSeek/通义千问）+ Prompt 工程 | ★ 低 | 强：输入报告文本，输出白话解读+风险说明 | **必做** |
| A2 | **肺结节/肺癌智能问答（RAG 知识库）** | 大模型 + 向量检索（指南共识文档入库） | ★★ 中低 | 强：回答"磨玻璃结节 6mm 要多久复查"有指南依据 | **必做** |
| A3 | **CT 报告文本自动结构化（NLP 信息抽取）** | 大模型 Function Calling / 结构化输出 | ★★ 中 | 强：粘贴报告原文，自动填结节登记表单 | **强烈推荐** |
| A4 | **CT 影像结节 AI 检测/分割** | MONAI 预训练模型（LUNA16，3D RetinaNet）独立 Python 推理服务 | ★★★★ 较高 | 很强：上传 CT 自动标出结节位置 | 加分项（有条件再做） |
| A5 | **失访/结节进展风险预测** | 传统 ML（XGBoost/逻辑回归）于结构化随访数据 | ★★★ 中 | 中：驾驶舱展示高风险失访患者名单 | 可选 |

### 11.2 各方案详细设计

#### A1：CT 报告智能解读（患者看得懂的报告）

- **场景**：患者端查看检查报告时，点击"AI 解读"，将报告文本（脱敏后）发送给大模型，返回通俗易懂的解读：结节是什么性质、恶性征象有没有、下一步建议、注意事项。
- **实现**：Spring Boot 新增 `ai-service`，通过 **Spring AI** 调用大模型。DeepSeek、通义千问、豆包、Kimi 等均兼容 OpenAI 接口规范，可用 `spring-ai-openai` 依赖统一接入，更换模型只改配置 [^38^][^48^]；若主用通义千问也可用 Spring AI Alibaba（阿里云百炼新用户有 100 万免费 Token，足够开发调试）[^44^]。
- **Prompt 设计要点**：系统提示词固定角色（胸外科随访助手）、要求基于报告内容不臆造、输出固定结构（结论/风险/建议/免责），末尾附"仅供参考，以医生诊断为准"。
- **合规红线**：AI 输出必须标注"辅助参考"，不替代诊断——这也是论文里"伦理与合规"章节的素材。

#### A2：指南知识库智能问答（RAG）

- **场景**：患者问"我这种结节危险吗""复查前要注意什么"；医生/随访专员问"部分实性结节 7mm 随访间隔"。
- **实现（RAG 检索增强生成）**：
  1. 把本报告第三章的随访规则、《肺结节诊治中国专家共识》等权威文档切分后做向量化（Embedding），存入向量库（轻量可选 Redis Stack / PgVector，也可用 Milvus）；
  2. 用户提问 → 向量检索召回相关段落 → 拼入 Prompt → 大模型基于召回内容作答并给出出处；
  3. Spring AI 原生支持 Embedding 与 VectorStore 抽象，与微服务栈无缝集成 [^48^]。
- **价值**：避免大模型"幻觉"编造医学建议，回答可溯源到指南——这是答辩时最能体现专业性的 AI 设计。

#### A3：CT 报告自动结构化（NLP 信息抽取）

- **场景**：随访专员拿到一份 CT 报告原文（非结构化文本），粘贴进系统，AI 自动抽取：结节位置、类型（实性/磨玻璃/部分实性）、最大径、密度、恶性征象、数量，自动回填"结节登记表单"，人工确认后入库。
- **实现**：利用大模型的结构化输出能力（JSON Schema / Function Calling），Spring AI 支持把响应直接绑定为 Java 实体类。抽取结果与系统字段一一对应，大幅降低录入工作量。
- **联动**：结构化结果自动触发随访规则引擎匹配模板 → 生成随访计划，形成"报告录入 → AI 抽取 → 自动排期"的完整智能闭环（很好的演示主线）。

#### A4：CT 影像结节检测（加分项）

- **技术现状**：肺结节检测是医学 AI 最成熟的方向之一。MONAI Model Zoo 提供在 LUNA16 公开数据集上训练的 **3D RetinaNet 预训练模型**（输入 192×192×80 的 CT patch，输出结节位置框与概率），可直接下载权重做推理，无需自己训练 [^42^][^45^]；学术上还有 nnU-Net 分割、YOLOv8-DLung（LUNA16 上 mAP 95.5%）等改进方案 [^34^][^51^]。
- **落地方式**：单独部署一个 **Python 推理服务**（FastAPI/Flask + MONAI），加载预训练权重；Spring Cloud 的 `nodule-service` 通过 HTTP 调用，或将其注册进 Nacos 统一治理 [^49^]。
- **前提条件**：需要能处理 DICOM/NIfTI 格式 CT 数据（可用 LUNA16 公开数据做演示），推理最好有 GPU（无 GPU 时小 patch CPU 推理较慢但可演示）。
- **建议**：若团队无深度学习基础或无 GPU，可降级为"上传结节截图 + 大模型多模态描述"，或把 A4 写进"未来展望"。

#### A5：失访/进展风险预测（可选）

- 用系统积累的结构化数据（年龄、结节大小/类型、历史随访依从性、症状上报频率）训练一个二分类模型（逻辑回归/XGBoost），预测"失访风险"或"结节进展风险"，在数据驾驶舱标注高风险患者优先干预。
- 演示数据不足时可用模拟数据训练，论文中如实说明即可。

### 11.3 微服务架构调整（在原方案基础上）

```
新增/调整：
├── ai-service（新增）
│    ├── LLM 接入层：Spring AI（OpenAI 兼容协议，可切换 DeepSeek/通义/豆包/Kimi）
│    ├── 报告解读：Prompt 模板 + 流式输出（SSE）
│    ├── 智能问答：RAG（Embedding + VectorStore + 指南文档库）
│    └── 报告结构化：结构化输出绑定 Java DTO
├── nodule-inference-service（可选，Python/FastAPI）
│    └── MONAI 预训练模型推理（CT 结节检测）
└── knowledge-base（数据层）
     └── 向量库（Redis Stack / PgVector / Milvus）+ 指南文档切片
```

**事件流示例（演示主线）**：
患者上传 CT 报告 → `ai-service` 结构化抽取 → `nodule-service` 生成结节快照 → `followup-service` 规则引擎匹配随访模板 → `notification-service` 推送复查提醒 → 患者端 AI 解读报告 + 随时向 AI 助手提问（RAG 依据指南回答）。

### 11.4 成本与可行性

- A1~A3 全部基于大模型 API，**无需 GPU、无需训练模型**，按 Token 计费（DeepSeek 价格极低，通义千问有免费额度 [^44^]），学生零门槛落地，推荐作为 AI 核心卖点。
- A4 需要 Python 深度学习环境和（最好）GPU，作为加分项。
- 全部 AI 功能对外统一走 `ai-service`，与业务服务解耦，符合微服务设计原则，答辩时可强调"AI 能力服务化、模型可插拔替换"。

## 十二、技术深度提升方案（应对"要有技术深度"要求）

> 原则：**深度 ≠ 堆砌中间件**。每一项深度技术都要回答"解决了什么实际问题"，并能拿出实验数据（压测/对比评测）写进论文。以下按"投入产出比"排序，标注【必做】【推荐】【可选】。

### 12.1 AI 方向的技术深度（四层楼，建议做到第 2~3 层）

**第 1 层（底线，不算深度）**：调通大模型 API + 写好 Prompt。只做这一层会被老师认为"套壳"。

**第 2 层：RAG 工程化【必做】**——把"接了个知识库"做成一个可评测的检索系统：

| 技术点 | 做法 | 论文素材 |
|---|---|---|
| 文档切分策略 | 按指南章节语义切分 vs 固定长度切分，保留标题层级元数据 | 切分策略对召回质量的影响分析 |
| **混合检索** | 向量检索（BGE Embedding，语义）+ BM25 关键词检索（ES/稀疏向量），RRF 融合——纯向量检索对"6mm""Lung-RADS 4A"这类精确术语会失效，这是必须用混合检索的理由 [^54^][^65^] | 检索架构设计图 |
| **Rerank 精排** | 混合检索先召回 4N 条候选，再用 bge-reranker-v2-m3 精排取 Top N；Rerank 服务挂掉时降级回原始排序保证可用性 [^65^] | 降级容错设计 |
| 引用溯源 | 回答附指南出处（文档名+章节），点击可定位原文 | 医疗场景的可信性设计 |
| **检索效果评测** | 人工构造 30~50 个肺结节随访问题作为评测集，对比"纯向量 vs 混合检索 vs 混合+Rerank"三组的召回准确率/回答正确率 | **消融实验表格——最有说服力的深度证据** [^62^] |

**第 3 层：Tool Calling 智能助手（Agent 化）【强烈推荐】**——让 AI 从"只能聊天"变成"能办事"：

- 把系统能力注册成工具：`查询我的随访计划`、`查询下次复查时间`、`上报症状`、`查询结节变化趋势`；
- 患者问"我最近复查结果怎么样，下次什么时候来"，大模型自主决策调用工具查询真实数据后整合回答——两步调用模式（模型决策调什么 → 后端执行 Java 方法 → 模型整合结果回答）[^68^]；
- Spring AI / LangChain4j 原生支持 Tool Calling，Java 方法加注解即可注册 [^55^][^64^]；
- **这是"AI 与业务系统深度融合"和"AI 套壳"的分水岭**，答辩演示效果极好。
- 配套：SSE 流式输出（逐字输出体验）、多轮对话记忆持久化（Redis）。

**第 4 层：模型微调与本地化部署【可选，有 GPU 再做】**：

- 用 **LLaMA-Factory** 对 DeepSeek-R1-Distill-Qwen-7B 做 LoRA 微调（冻结基座、只训低秩矩阵，单卡 T4/Colab 即可完成），数据集可用公开的 medical-o1-reasoning-SFT 医疗推理数据集 + 自建肺结节随访 QA 数据 [^66^][^69^][^70^]；
- 微调后模型合并导出，用 Ollama/vLLM 本地部署，`ai-service` 通过 OpenAI 兼容协议调用——**实现"数据不出院"的隐私合规卖点**；
- 论文可做"微调前 vs 微调后"在自建评测集上的对比实验。

### 12.2 微服务架构方向的技术深度（按业务痛点选型）

| # | 技术点 | 解决的本系统真实痛点 | 深度体现 |
|---|---|---|---|
| B1 | **RocketMQ 延迟消息**【必做】 | 复查提醒要在"未来某个精确时间点"触发（7 天后/3 个月后）。对比三种方案：定时任务轮询扫库（实时性差、扫表压力）/ Redis ZSet 时间轮 / MQ 延迟消息，给出选型理由 | 方案对比表——经典论文素材 |
| B2 | **MQ 可靠性三件套**【必做】 | 提醒消息不能丢不能重：生产者事务消息/本地消息表、消费者**幂等消费**（防重复发短信）、死信队列兜底 | 分布式消息可靠性设计 |
| B3 | **Caffeine + Redis 多级缓存**【推荐】 | 随访模板、字典、驾驶舱统计是高频读：本地缓存抗热 key + Redis 二级 + 缓存穿透（布隆过滤器）/击穿/雪崩处理 | **JMeter 压测：加缓存前后 QPS/RT 对比图** |
| B4 | **Redisson 分布式锁**【推荐】 | 防止定时任务多实例并发扫描时重复生成随访计划/重复推送；也可用 Redisson 实现"同一患者建档"防并发重复提交 | 并发安全性设计 |
| B5 | **Seata 分布式事务**【可选】 | "建档 + AI 抽取结节 + 生成随访计划"跨 3 个服务，用 Seata AT 模式保证一致性；或用本地消息表做最终一致性并说明取舍 | 分布式事务方案选型论证 |
| B6 | **Sentinel 熔断限流降级**【必做，成本极低】 | 大模型 API 不稳定/有限流：ai-service 超时熔断、降级为"AI 服务暂不可用，请稍后再试"并记录待重试；网关层限流防刷 | 服务治理 + AI 场景的熔断设计 |
| B7 | **SkyWalking 链路追踪 + 聚合日志**【推荐】 | 微服务下排查"一次建档调用经过哪些服务、慢在哪"，全链路 TraceId | 可观测性架构图 |
| B8 | **随访规则引擎抽象**【强烈推荐】 | 指南随访规则（第三章表格）不写成 if-else 硬编码，抽象成"条件项 + 结论"的决策表存库，运行时匹配——指南更新只改数据不改代码 | **规则引擎设计模式（表驱动法），最能体现设计功底的一项** |
| B9 | XXL-Job 分布式调度【推荐】 | 逾期随访每日扫描、失访自动标记，分片广播避免多实例重复执行 | 与 B1/B4 联动 |
| B10 | ShardingSphere 分库分表【可选】 | 随访任务/消息记录表数据量大，按患者 ID 分片；毕设数据量小可写进"扩展性设计"章节 | 可只做设计论证不实现 |

### 12.3 推荐的"深度组合包"（投入产出比最优）

```
AI 线：RAG 工程化（混合检索+Rerank+引用溯源+消融评测）   ← 深度主力
     + Tool Calling 智能助手 + SSE 流式输出             ← 演示主力
架构线：B8 规则引擎（表驱动）                              ← 设计功底
     + B1+B2 RocketMQ 延迟消息+幂等+死信                ← 分布式功底
     + B3 多级缓存 + JMeter 压测对比                     ← 性能功底
     + B6 Sentinel + B7 SkyWalking                      ← 微服务治理
     + B4 Redisson 分布式锁 + B9 XXL-Job                 ← 顺手带上
进阶（有 GPU）：LoRA 微调医疗模型 + 微调前后对比实验       ← 冲优秀论文
```

### 12.4 写进论文/答辩的"证据"清单

1. **RAG 消融实验表**：纯向量 / 混合检索 / 混合+Rerank 三组准确率对比；
2. **缓存压测图**：JMeter 对随访工作台接口压测，加缓存前后 QPS、平均 RT 曲线；
3. **消息可靠性验证**：模拟消费者宕机/重复投递，展示幂等与死信兜底；
4. **熔断降级演示**：断掉大模型 API，系统优雅降级而非雪崩；
5. **AI 助手办事演示**：一句自然语言 → 自动查库 → 给出个性化回答；
6. （可选）**微调对比实验**：通用模型 vs 微调模型回答随访问题的质量评分。
