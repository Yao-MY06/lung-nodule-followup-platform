# F2 提醒与失访闭环（延迟消息 / 幂等 / XXL-Job 扫描）

> 文档类型：跨模块流程　所属模块：followup+notification　依赖文档：[global/30 §6/§8, modules/followup, modules/notification]
> 版本：v1.0（2026-08-22）　阅读优先级：高　风险车道：黄区（消息可靠性是论文深度点）

## 流程目标

复查提醒在"未来精确时间点"可靠触达（不丢、不重），逾期与失访患者被系统性识别并转入人工追踪。

## 链路一：到点提醒（延迟/定时消息）

```
followup（任务生成时）                    RocketMQ 5.x               notification
  为每个 task 计算 T-7/T-3/T-1
  → 投递定时消息(deliverTime=计划日期-偏移)
     msgKey = "taskId:REMIND_T7"  ──────▶ 定时暂存 ──到点──▶ 消费者:
  XXL-Job 每小时对账：任务存在且未提醒                ├─ 幂等: SETNX bizKey + message_record uk
  而消息缺失 → 补投(同 bizKey)                       ├─ 站内信落库(即成功)
                                                     ├─ 短信异步(可选渠道, 失败重试1/5/30min)
                                                     └─ 重试3次失败 → 死信队列 → 告警人工补发
```

## 链路二：逾期与失访（XXL-Job 每日 02:00，分片广播）

```
扫描 followup_task（索引 idx_scan(status,plan_date)，按 patient_id 取模分片）:
  status=0/1 且 plan_date < today-7   → status=2 逾期，NotifyApi 通知主管医生
  status=2 且 plan_date < today-30    → 状态转疑似失访（标记，进入失访名单）
  remind_sent ≥3 且仍逾期             → status=4 失访，档案 stage_label 同步"失访"
随访专员电话追踪 → followup_record 记录结果:
  ├─ 联系上并补完成复查 → 任务完成，恢复随访（stage_label 回"结节随访中/术后随访中"）
  └─ 确认退出 → 结案流程
```

## 关键设计决策

| 决策 | 理由 |
|---|---|
| **生产端默认"扫描派发"**（P3 实现决策） | rocketmq-spring-boot-starter 2.3.1 的 delayLevel 上限 2 小时，无法表达天级定时；采用 XXL-Job 每分钟扫描到期提醒点（T-7/T-3/T-1）→ 发**即时** `YILIAO_REMIND_DUE` 消息。消费端幂等三保险完全不受生产端方式影响；论文 B1 三方案对比（扫库/Redis ZSet/MQ 定时）以本取舍为素材，`remind.mode` 预留 5.x 定时消息升级 |
| 定时消息 vs 定时任务轮询扫库 | 扫库实时性差（分钟级轮询）且全表扫描压力大；MQ 定时到点精确、天然削峰——论文选型对比素材 |
| XXL-Job 对账补投（每小时） | 弥补"消息可能未投出/丢失"，bizKey 幂等保证补投不重复发送——双保险 |
| 提醒状态跟随任务而非消息 | remind_sent 计数在 followup_task 上，Job 与消费端都能判断真实进度 |
| 短信与站内信解耦成败 | 短信是外部依赖（厂商故障不该让提醒"失败"）；站内信本地事务即达 |

## 异常场景

- 消费者宕机：消息 ACK 前挂掉 → MQ 重投；幂等键拦截重复发送。
- 患者已结案/任务取消后消息到点：消费前查任务当前状态，非待提醒状态直接丢弃（终态校验）。
- 重复投递演示场景（论文用）：手工重发同一 bizKey 消息 → 观察 message_record 仅一条。
