## 二、缺陷根因与修复

- **根因**：`PatientTools`（`@Component`）声明两个构造器——public 双参 `(FollowupApi, NoduleApi)`（R1 修复新增 forPatient 快照设计的一部分）与 private 四参，均无 `@Autowired`。Spring 对多构造器且无主构造器标注的 bean 走 `instantiateBean()` 默认无参路径，类中无无参构造器 → 装配失败。确定性缺陷，与 LLM Key/数据源无关（失败发生在 LLM 连通验证之前的装配阶段）。
- **为何单测没拦住**：`ChatServiceTest` 对 PatientTools 用 `@Mock`，`PatientToolsTest` 直接 `new PatientTools(...)`，全模块无上下文装载用例——"单测全绿但启动失败"盲区。
- **修复（方案 A，最小改动）**：`yiliao-ai/src/main/java/com/yiliao/ai/tools/PatientTools.java` 给 public 双参构造器加 `@Autowired` + 行 javadoc 说明（含日期与后果），其余代码零改动。保留 `@Component` 基座 bean + `forPatient(id)` 请求级视图的既有设计。
- **盲区补测**：新建 `yiliao-ai/src/test/java/com/yiliao/ai/tools/PatientToolsWiringTest.java`——`AnnotationConfigApplicationContext` 注册 FollowupApi/NoduleApi 两个 mock bean + `register(PatientTools.class)` + refresh，断言 `getBean(PatientTools.class)` 可装配。无 DB/LLM/Nacos 依赖。若未来回退（删掉 `@Autowired`）该用例必失败。
- **测试结果**：`mvn test -pl yiliao-ai` → **Tests run: 33, Failures: 0, Errors: 0**（存量 32 + 新增 1），BUILD SUCCESS。
- **启动验证**：修复后 `mvn -pl yiliao-ai spring-boot:run`（3307 数据源、DeepSeek 环境变量注入）21:07 启动，`/actuator/health` → `{"status":"UP"}`。

## 七、遗留问题（需主线决策）

1. **P1 传输层 403 不可达（医生端 403 行为变更）**：SSE 端点（`produces=text/event-stream`）抛 BizException 时，JSON 异常体无法按 SSE Accept 协商 → 500 空体；`Accept: */*` 时为 200+业务码 403 体（项目统一返回体惯例本就是"HTTP 200 + 业务码"，与该惯例一致）。安全语义已达标（拦截+无 LLM 调用），是否要求字面 HTTP 403 需决策；若要，需为 SSE 端点定制异常解析（`SseEmitter` 前置校验或 `@ExceptionHandler(produces=...)`），属 yiliao-common-web/ai 两处改动。
2. **Key 轮换建议**：DeepSeek Key 已在多轮代理会话环境变量中出现，建议本轮验证结束后轮换。本次所有落盘文件 `grep sk-` 自查零泄漏（见下）。
3. **"装配冒烟测试"是否推广到全服务**：连续两轮（R1、T4 首轮）"单测全绿+运行期失效"且失效点已前移到启动期。建议把 `PatientToolsWiringTest` 模式（最小上下文注册核心 @Component）推广到九服务并纳入合入门禁——涉及 specs/global 变更，按黄区流程签核。
4. **T5 话术误标**：服务端身份绑定未被绕过（数据零泄露），但 LLM 会把"本人数据"在话术上冠以注入的患者 id。可考虑在系统提示词中强化"查询结果仅表述为当前登录患者本人的数据"，低成本缓解演示观感风险。
