## 一、熔断降级演示

### 1.1 演示原理（事实依据，代码已实现于 P4）

specs/modules/ai.md §4 规则 5 降级链：**LLM 挂/超时 → 降级返回，不向医生工作流抛错**。当前为代码级降级（`yiliao-ai` 已实现，无需真实 LLM、无需 Sentinel 规则即生效）：

| 场景 | 触发 | 实际表现 | 代码位置 |
|---|---|---|---|
| A3 抽取 | LLM 不可达/坏 JSON | 重试 1 次（附纠错提示）→ 仍失败 → `Result{code:24002, msg:"报告抽取失败，请手动录入"}`，不阻塞人工录入 | `ReportExtractService.extract` |
| A1 解读 | LLM 异常 | SSE 流内优雅降级：`delta` 事件输出"AI 服务暂时不可用，请稍后再试或联系您的医生"（24001 文案），随后 `done:[DONE]`，连接正常关闭无 500 | `ReportInterpretService.interpret` |

故障注入方式：**不改代码不改文件**，用环境变量把 LLM 指向不可达地址（`application.yml` 中 `base-url/api-key` 均有 `${YILIAO_LLM_*}` 环境变量占位）。

### 1.2 步骤 A：ai-service 代码级降级演示（LLM 故障注入）

**前置**：`cd docker && docker compose up -d`（mysql/redis）；本地启动 yiliao-auth、yiliao-ai、yiliao-gateway。

1. 用环境变量启动 ai-service（模拟"LLM 服务挂"）：
   - Git Bash：`YILIAO_LLM_BASE_URL=http://127.0.0.1:9999 YILIAO_LLM_API_KEY=sk-fake-degradation-demo mvn spring-boot:run -pl yiliao-ai`
   - PowerShell：先 `$env:YILIAO_LLM_BASE_URL="http://127.0.0.1:9999"; $env:YILIAO_LLM_API_KEY="sk-fake-degradation-demo"` 再 IDE/命令行启动
   - 127.0.0.1:9999 无服务 → 连接拒绝 → `LlmClient` 抛异常 → 走降级分支。
2. 登录拿 Token（admin/admin123 为 `docker/init-sql/yiliao_auth.sql` 种子开发账号）：
   ```bash
   curl -s -X POST http://localhost:8080/api/auth/login -H "Content-Type: application/json" \
     -d '{"username":"admin","password":"admin123"}'   # 取 data.accessToken
   ```
3. **场景一 抽取降级**：
   ```bash
   curl -s -X POST http://localhost:8080/api/ai/report/extract \
     -H "Authorization: Bearer {accessToken}" -H "Content-Type: application/json" \
     -d '{"rawText":"右肺上叶见一枚部分实性结节，最大径约8mm，实性成分约4mm，边缘毛刺。"}'
   ```
   **预期**：HTTP 200，body `code=24002, msg="报告抽取失败，请手动录入"`（含 1 次重试，等待数秒属正常）。
4. **场景二 解读降级**：
   ```bash
   curl -N -X POST http://localhost:8080/api/ai/report/interpret \
     -H "Authorization: Bearer {accessToken}" -H "Content-Type: application/json" \
     -d '{"rawText":"右肺上叶部分实性结节，最大径8mm。"}'
   ```
   **预期**：SSE 输出 `event:delta`，data 为"AI 服务暂时不可用，请稍后再试或联系您的医生"，随后 `event:done data:[DONE]`；无 500、无异常堆栈到前端。
5. **恢复验证（可选，答辩加分）**：去掉两个环境变量重启 ai-service，重新请求恢复正常 → 证明故障注入可逆、降级逻辑与正常链路隔离。
6. **截图留证**：①extract 响应 JSON（code=24002）②interpret SSE 降级文案 ③ai-service 控制台 Warn 日志（"抽取重试仍失败"/"解读降级"，佐证异常被捕获而非泄漏）。

### 1.3 步骤 B：Sentinel 控制台 + 网关流控规则演示

1. **起控制台**：`docker/docker-compose.yml` 文末取消 `sentinel-dashboard` 注释块（取消注释后给服务命名为 `sentinel-dashboard`），执行：
   ```bash
   cd docker && docker compose up -d sentinel-dashboard
   ```
   浏览器打开 http://localhost:8858（bladex 镜像默认账号 sentinel/sentinel）。
2. **接入网关**：取消 `yiliao-gateway/src/main/resources/application.yml` 中 `# dashboard: localhost:8858` 的注释，重启网关；控制台左侧出现 `yiliao-gateway`。
3. **造流量**：JMeter 打登录接口 10 并发 × 60s（脚本 `tasks/jmeter/yiliao-login.jmx`，用法见其 README）。
4. **配规则**：控制台 → 簇点链路 → 资源 `/api/auth/login` → 点"＋流控"→ 阈值类型 **QPS**、单机阈值 **10**。
5. **验证限流**：把线程数改 50（README §改并发）再跑一轮 → 观察部分请求被拒。
   **如实说明**：网关尚未注册 BlockException → 统一返回体的转换处理器（P5 后续代码任务；specs/modules/gateway.md §4 约定超限返回 `Result{code:11001}`）。**接入前**被限流请求表现为 **HTTP 429 + `Blocked by Sentinel (flow limiting)`**；**接入后**为 `Result{code:11001}`。两种表现均为"限流生效"的有效证据。
6. **截图留证**：①控制台流控规则列表（QPS=10）②JMeter 聚合报告 Error% > 0 ③单个被限流请求的响应体（429 文本或 11001）④控制台"实时监控"QPS 曲线被削平在 10 附近。

### 1.5 答辩口径

- 两层防护：代码级降级（毫秒级同步兜底，一定生效）+ Sentinel 规则（可视化、可热更、可按资源精细配置）。

## 二、JMeter 压测方案（论文对比图数据源）

### 2.1 目标接口（全部经网关 8080，压测同机部署）

| # | 接口 | 方法 | 鉴权 | 压测关注点 |
|---|---|---|---|---|
| 1 | `/api/auth/login` | POST | 免鉴权（白名单） | BCrypt 密码校验 CPU 密集，观察 RT 与 CPU |
| 2 | `/api/followup/workbench?status=1&page=1&size=10` | GET | 需 Token | 医生高频列表查询，DB 分页联表 |
| 3 | `/api/stats/overview` | GET | 需 Token | 聚合统计，**P5b 加缓存前后对比主战场** |

### 2.2 线程组设计

- **三档**：10 / 50 / 100 并发 × Duration 60s；Ramp-up 10s（即每秒起 1/5/10 个线程）。
- 循环方式：Forever 循环 + 调度器按 60s 截止（脚本内 `LoopController.continue_forever=true` + `ThreadGroup.scheduler=true, duration=60`，GUI 显示"无限循环 + 持续时间 60 秒"）。
- 换档只改一处：`ThreadGroup.num_threads`（GUI 线程数，或文本编辑 jmx）。

### 2.3 命令行执行方式

```bash
cd tasks/jmeter
# 10 并发档
jmeter -n -t yiliao-login.jmx -l result-login-10.jtl -e -o report-login-10
# 50 / 100 并发档：先改 num_threads 为 50/100，再换输出名执行
jmeter -n -t yiliao-login.jmx -l result-login-50.jtl -e -o report-login-50
jmeter -n -t yiliao-login.jmx -l result-login-100.jtl -e -o report-login-100
```

注意：`-o` 报告目录必须不存在或为空；`-l` 的 jtl 文件不可复用已有文件。

### 2.4 指标（HTML 报告 → Statistics 表）

| 指标 | 报告字段 | 论文用途 |
|---|---|---|
| 平均响应时间 | Average (ms) | 基础对比 |
| P95 响应时间 | 95th pct | **主指标**：尾延迟随并发增长曲线 |
| 吞吐量 | Throughput (/sec) | QPS 随并发档位变化、拐点 |
| 错误率 | Error % | 稳定性；非限流场景应≈0 |

### 2.5 带鉴权接口的压测（workbench / stats）

1. 先登录取 accessToken（§1.2 第 2 步）；access Token 有效期 2h（`yiliao.jwt.access-ttl-seconds: 7200`），60s 一轮的压测单 Token 足够。
2. 改脚本：`HTTPSampler.path` 改为目标路径、`HTTPSampler.method` 改 GET、删除 body 的 HTTPArgument（详见 `tasks/jmeter/README.md`）；并在 HeaderManager 增加一行 `Authorization: Bearer {accessToken}`。
3. **压测前确认 Sentinel 流控规则已删除或阈值调大**，避免限流干扰 RT/错误率统计（除非正在演示 §1.3）。

### 2.6 P5b"加缓存前后对比"接入点（论文压测对比图）

- statistics-service `/api/stats/overview` 首版直查多表聚合；P5b 接入 Redis/Caffeine 缓存（建议 TTL 60s，驾驶舱容忍分钟级延迟）。
- 对比方法：**同一档位（建议 50 并发 × 60s）**改代码前压一轮存 `report-overview-before/`，加缓存后同参数再压一轮存 `report-overview-after/`。
- 产图：分别截图两份 HTML 报告 Statistics 表（P95、Throughput、Error%），论文并列展示；预期缓存命中后 P95 显著下降、QPS 上升、DB 压力下降。

### 2.7 环境与口径说明

- 压测机与被测服务同机（毕设环境）：答辩口径为**单机相对对比**，不宣称绝对容量。
- 版本：JMeter 5.6+（jmx 为 5.6 标准格式）；报告统一用命令行 `-e -o` 生成 HTML，不用 GUI 跑压测。
