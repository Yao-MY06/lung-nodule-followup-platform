# 团队治理规范

本文件是可选的团队层规则。个人使用时可只保留 `README.md`、`AGENTS.md`、模板和清单；启用团队协作时，把以下规则纳入仓库评审和合并门禁。

## 十条规则

1. **上下文文件即代码**：`AGENTS.md`、工具规则和共享 Skill 纳入版本控制，变更走普通评审；根目录上下文是高层项目事实的权威来源。
2. **组合工具而非单一标准**：按任务选择补全、代理和探索工具，但统一使用同一套仓库规则、模板和证据要求。
3. **显式约定工作模式**：在任务简报中注明是结对式补全还是委托式代理，统一交接和审查预期。
4. **PR 预筛查**：PR 描述包含 AI 使用披露、风险车道、自动化结果、安全扫描、依赖核验和作者亲自验证的内容。
5. **红黄区升级**：黄区至少由资深工程师签核；红区必须增加安全角色双审，无“代理已通过”豁免。
6. **安全门禁自动化**：在项目支持的范围内把密钥扫描、依赖核验和 SAST 放入 pre-commit 或 CI；政策文字不能替代可执行门禁。
7. **测试归属清晰**：AI 不单独决定自己代码的测试边界；测试由人或独立流程先提出，作者对失败和遗漏负责。
8. **并行代理双检查点**：规格批准后才启动 Worker；Worker 验证通过后仍需人工审查再合并。
9. **看交付健康而非产量**：关注 DORA、缺陷、返工、评审队列、代码流失和重复率，不用代码行数、token 或 PR 数代表生产力。
10. **技能复利**：共享 Skill 和上下文库由团队维护；新人先读 `AGENTS.md`、本文件和相关清单，再开始委托代理任务。

## PR 最小披露

```text
AI 使用：{{未使用 / 补全 / 委托代理 / 多代理}}
风险车道：{{绿 / 黄 / 红}}
规格或任务简报：{{路径}}
作者亲自验证：{{逐行 diff、测试、手工场景等}}
独立审查者：{{姓名或角色}}
```

## 责任边界

- 作者负责理解变更、提供验证证据和完整披露。
- 资深审查者负责检查架构、边界和维护成本。
- 安全审查者负责红区的威胁、权限、数据和供应链风险。
- 仓库维护者负责保持上下文、清单和自动化门禁一致。
